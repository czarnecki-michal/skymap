# Karta Mapa nieba v2 – plan implementacji

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Przebudowa karty na nowoczesny, płynny widok nieba (Canvas 2D, rozglądanie się, konstelacje, dzień/noc, animacja) z opcjonalnym zdjęciem w perspektywie i kreatorem kalibracji (po gwiazdach z EXIF albo po kompasie).

**Architecture:** Czysta logika karty (widok, wygląd nieba, homografia, solver, EXIF, scena, stan kreatora) w osobnych modułach TS testowanych w Vitest; cienkie warstwy rysowania (canvas) i UI (Lit). Integracja dostaje rozszerzone `mapa_nieba/sky`, endpoint zdjęcia i zapis `photo_opacity`. Rzut `project/unproject` z v1 zostaje bez zmian (wspólne wektory Python↔JS).

**Tech Stack:** Lit + TypeScript 5.6 + Rollup + Vitest/happy-dom (karta); Python 3.13, HA 2026.x, skyfield, pytest-homeassistant-custom-component w WSL (`~/mn-venv`).

**Spec:** `docs/superpowers/specs/2026-11-17-karta-v2-design.md` (na bazie `2026-11-17-mapa-nieba-design.md`)

## Global Constraints

- Sensory i ich reguły bez zmian; geometria okna i przeszkody nadal w opcjach config entry, zapis przez `mapa_nieba/save_geometry`.
- Rzut rektyliniowy z `projection.ts`/`geometry.py` bez zmian; `tests/fixtures/projection_vectors.json` musi dalej przechodzić.
- Bez WebGL/three.js; jedyna zależność runtime karty: `lit`.
- Zoom widoku 20–120°, roll widoku = 0; ⌖ ustawia widok = geometria okna.
- Przezroczystość zdjęcia domyślnie 0.6; YAML `photo` ma pierwszeństwo przed zdjęciem z integracji.
- DPR canvasa ograniczony do 2; przerysowanie tylko przy interakcji/animacji/nowych danych.
- Czas EXIF bez strefy interpretowany w strefie HA (`hass.config.time_zone`), chyba że jest `OffsetTimeOriginal`.
- Teksty UI po polsku.
- Testy Pythona: `wsl.exe -d ubuntu -- bash -lc 'cd /mnt/c/Users/mcz/OneDrive/mapa_nieba && ~/mn-venv/bin/python -m pytest tests -q -p no:cacheprovider'`; karta: `cd card && npm test`.

## Review Focus

1. Dwa punkty kalibracji prawie w tym samym miejscu albo ten sam obiekt dwa razy → solver zwraca błąd z komunikatem, nie absurdalną geometrię. (Task 8)
2. Zdjęcie bez EXIF (HEIC, zrzut ekranu) → kreator prosi o ręczną godzinę, nie przyjmuje po cichu czasu wgrania. (Task 9, 10)
3. Rozglądanie się tak daleko, że narożnik zdjęcia jest za obserwatorem → zdjęcie ukryte, brak NaN w `matrix3d`. (Task 5)
4. Wgranie zbyt dużego lub nie-obrazkowego pliku → odrzucone z komunikatem. (Task 2)
5. Przeciąganie przez azymut 0/360 i w okolice zenitu → widok zawinięty/ograniczony (alt ≤ 89°), bez skoków. (Task 4)

### Task 8: Solver kalibracji

**Files:** Create: `card/src/solver.ts`; Test: `card/test/solver.test.ts`.

**Interfaces:** Consumes: `project`. Produces: `type Match = {az: number; alt: number; x: number; y: number}` (x, y znormalizowane na zdjęciu); `solveGeometry(start: WindowGeometry, matches: Match[]): {geometry: WindowGeometry; error: number} | {fail: string}` – 1 dopasowanie: niewiadome `az_center, alt_center`; 2: także `hfov, roll`; Gauss–Newton z numerycznym jakobianem, maks. 50 iteracji; `fail` gdy dopasowania są < 3° od siebie na niebie lub < 0.05 od siebie na zdjęciu, lub gdy brak zbieżności (błąd końcowy > 0.01).

- [ ] **Step 1:** Testy: geometria prawdziwa `(140, 20, 72, 4/3, 4)`; z niej `project` dwóch obiektów → solver startujący z `(120, 10, 67, 4/3, 0)` odtwarza wszystkie parametry ±0.1°; 1 dopasowanie odtwarza az/alt przy znanym hfov i roll; dwa identyczne dopasowania → `fail`; dopasowanie przez północ (prawdziwe az 355) działa.
